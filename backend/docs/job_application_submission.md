## API contract

**POST `/api/applications`**

Required header: `Authorization: Bearer <SUPABASE_ACCESS_TOKEN>`.

JSON body:

```json
{
  "job_id": 42,
  "resume_id": "8cb0abe6-2c39-45dc-a700-3cf2bd28592c",
  "cover_letter": "I am interested in this role."
}
```

- `job_id` is required and must be a positive integer, matching `GET /api/jobs/<int:job_id>`. A digit-only string is also accepted.
- `resume_id` is optional, but if supplied it must be a UUID belonging to the logged-in user.
- `cover_letter` is optional, string only, at most 2,000 characters.
- The `applicant_id` **always comes from verified Supabase Auth**, never from the request body.
- Newly created application status: `Applied`.

Successful response: HTTP **201** with `message` and `application` (`id`, `applicant_id`, `job_id`, `resume_id`, `status`, `submitted_at`).

Error responses: **400** invalid JSON/inputs, **401** missing/invalid authentication, **404** job not published or resume not owned, **409** duplicate submission (enforced by database unique constraint), **500** database or configuration problem.

## Schema contract - NEEDS CONFIRMATION WITH HATEM

**Important: the supplied `develop (8)` repository does not contain job or application table migrations.** The following is an integration assumption, not a claim about the existing database. No schema is created by Parsa's submission change.

The SQL currently expects:

```text
public.jobs
  id           integer/bigint primary key -- confirm exact integer type
  status       text -- eligible value: 'published'

public.applications
  id           uuid primary key (generated by database)
  applicant_id uuid not null (Supabase Auth user ID)
  job_id       integer/bigint not null  -- FK to jobs.id
  resume_id    uuid nullable
  cover_letter text nullable
  status       text not null -- initial 'Applied'
  created_at   timestamptz not null (default now())
  UNIQUE(applicant_id, job_id)

public.resumes
  id           uuid primary key
  profile_id   uuid -- used by existing Flask resume endpoint as owner
```

**Confirm before merging:**

1. Confirm Hatem's actual job primary-key integer type and that the availability value is `published`, as in the latest team's `GET /api/jobs` endpoint.
2. Hatem's application table, status constraints, required columns, FK relationships, and uniqueness rule.
3. Resume ownership column: current Flask implementation reads `resumes.profile_id`, but older migrations use `user_id`; reconcile against the actual deployed schema. This route's optional `resume_id` check assumes `profile_id`.
4. PostgreSQL access permissions/RLS: this backend uses the existing server-side `get_connection()` via `DATABASE_URL` plus a Supabase-verified user ID. The DB role must permit these queries, and authorization/RLS rules must be reviewed before deployment. Never expose the database connection string to the frontend.
5. Whether submitting without a resume is allowed; the Sprint 2 feature specification does not explicitly require an uploaded resume for every application.

If the confirmed schema differs, update *only the new submission module* and its tests; do not modify Hatem's migrations in this PR.

## Test locally

From the repository root (after installing Python dependencies):

```powershell
python -m pip install -r backend/requirements.txt
cd backend
python -m unittest discover -s tests -v
```

This unit suite uses mocked database/Supabase clients. It verifies request validation, authentication enforcement, ownership checks, successful creation, duplicate handling, and DB failures. **Mock tests do not establish a real Supabase/Postgres integration.**

## Manual integration validation (after Hatem's schema is available)

1. Use a confirmed real Supabase access token in the Authorization header.
2. Ensure there is a published job in the database; note its integer ID.
3. POST a valid application; expect **201**, correct `applicant_id`, and status `Applied`.
4. Check the database record matches the authenticated account.
5. Repeat the same submission; expect **409** (requires unique constraint).
6. Try without authorization; expect **401**.
7. Try an unpublished/unavailable job; expect **404**.
8. Try a resume belonging to a different account; expect **404**.
9. Run the pre-existing authentication/profile/resume test suites to check for regressions.
