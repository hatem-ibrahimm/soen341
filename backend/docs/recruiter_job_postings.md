## Authentication and security

Every endpoint requires `Authorization: Bearer <Supabase access token>`.

The user must have **administrator-controlled** Supabase `app_metadata.role == "recruiter"` or `app_metadata.roles` containing `"recruiter"`. **Do not** use `user_metadata`, request-body `role`, or `profiles.title` to grant this permission. `app_metadata` must be assigned by trusted administration; ordinary job seekers are rejected (HTTP 403). No recruiter-role assignment API is included here.

Owner IDs always come from verified auth tokens. SELECT/UPDATE queries always constrain `recruiter_id` to that authenticated owner; job ID in another account is returned as HTTP 404. Production DB role and RLS permissions still need review with Hatem.

## API endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/recruiter/jobs` | Create owned job posting (201) |
| `GET` | `/api/recruiter/jobs` | List authenticated recruiter's postings (200), including draft/closed |
| `GET` | `/api/recruiter/jobs/<int:job_id>` | Retrieve single owned posting (200 or 404) |
| `PATCH` | `/api/recruiter/jobs/<int:job_id>` | Edit owned job posting, including status (200 or 404) |

Example request:

```http
POST /api/recruiter/jobs
Authorization: Bearer <TOKEN>
Content-Type: application/json
```

```json
{
  "title": "Junior Software Developer",
  "company_name": "ExampleCo",
  "description": "Contribute to internal tools.",
  "location": "Montreal",
  "category": "Software Engineering",
  "required_skills": ["Python", "Flask"],
  "min_salary": 60000,
  "max_salary": 85000
}
```

- Required nonempty text: `title`, `company_name`, `description`, `location`, `category`.
- Optional: `required_skills` as array of strings (maximum 30 items), `min_salary` and `max_salary` as nonnegative numbers or null.
- Optional `status`: `draft`, `published`, `closed`. **Default: `draft`**. The team job search feature displays only `published` postings.
- `PATCH` accepts any nonempty subset of editable fields and rejects unknown/protected fields (including `id`, `recruiter_id`, `created_at`).
- `GET` list supports `status`, `limit` (1–100, default 20) and `offset` (0–100000, default 0). Response includes `jobs` and `pagination` with `has_more`.
- Response uses the job columns in the provisional SQL contract and `created_at` in ISO 8601.
- Possible errors: 400 validation, 401 unauthenticated, 403 not recruiter, 404 posting missing/not owned, 500 database/schema failure.

## Provisional database contract: MUST CONFIRM WITH HATEM

The repository snapshot includes a job-listing handler that queries `public.jobs`, but it does **not** include a definitive migration for `jobs`/`applications`. **This change does not create or alter tables.** The new module expects:

```text
public.jobs
  id              integer/bigint PRIMARY KEY (generated by DB)
  recruiter_id    UUID NOT NULL (Supabase Auth user ID)
  title           text NOT NULL
  company_name    text NOT NULL
  location        text NOT NULL
  category        text NOT NULL
  description     text NOT NULL
  required_skills text[] NOT NULL DEFAULT '{}'
  min_salary      numeric NULL
  max_salary      numeric NULL
  status          text NOT NULL DEFAULT 'draft'
  created_at      timestamptz NOT NULL DEFAULT now()
```

Required status values: `draft`, `published`, `closed`. Existing `GET /api/jobs` lists only `published` rows, and Issue #41 accepts applications only to `published` jobs. Issue #42 uses `jobs.recruiter_id` to authorize application status changes. **Do not merge without coordinating those shared contracts.**

Questions for Hatem and the team:

1. Is `jobs.id` integer/bigint and is `jobs.recruiter_id` a UUID referring to `auth.users.id`?
2. Do fields match the listing API and the proposed `required_skills text[]` column? If skills use a separate relation or JSONB, adapt the module accordingly.
3. Do job statuses include `draft`, `published`, and `closed`, and are additional posting lifecycle rules needed?
4. How will trusted administrators assign `app_metadata.role="recruiter"` to real recruiter accounts?
5. Which PostgreSQL connection role executes Flask SQL, and are its permissions/RLS policies correct?

## Acceptance-test issue suggestions

The Sprint 2 instructions require at least **two linked/labeled acceptance-test GitHub issues per user story**.

- **AT-43A — Recruiter creates and publishes job:** Given a recruiter with a valid token, when a valid posting is created and its status updated to `published`, then the posting is persisted under that recruiter's ID and appears in public job search.
- **AT-43B — Job seeker cannot manage recruiter postings:** Given a job seeker or different recruiter, when POST/GET/PATCH is attempted, then recruiter-only operations are denied and another recruiter's posting is never disclosed or changed.
